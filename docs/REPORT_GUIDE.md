# 报告解读指南

本指南帮助你正确理解 Self-Awakening 生成的审计报告，避免误读和过度推断。

## 报告核心结构

审计报告包含以下层级：

```
Audit Report
├── 摘要 (Summary)
│   ├── 探针总数、可评分数、准确率
│   ├── 平均延迟、输出长度
│   └── 基线相似度与置信等级
├── 基线比对 (Baseline Comparison)
│   ├── 与每个基线的相似度分数 (0-1)
│   ├── 置信等级 (high / medium / low)
│   └── 关键差异点列表
└── 逐探针证据 (Probe Evidence)
    ├── 每道题的正确性、延迟、得分
    ├── 选项一致性验证
    └── 哈希匹配状态
```

## 置信等级定义

| 等级 | 相似度范围 | 含义 |
|------|-----------|------|
| **high** | ≥ 0.85 | 强烈支持该基线身份，误判概率低 |
| **medium** | 0.60 ~ 0.84 | 中等支持，需结合更多证据判断 |
| **low** | < 0.60 | 不支持该基线，可能为其他模型 |

### 置信等级的决定因素

置信等级不仅取决于最终相似度分数，还受以下因素影响：

1. **探针数量**：运行探针越多，置信度越高（8 题 vs 51 题的结论可信度不同）
2. **温度参数**：`temperature=0` 时结果更稳定，置信度更高
3. **运行时参数一致性**：基线与待测运行使用相同的 temperature、max_tokens 时可比性更强
4. **错误率**：大量 `empty_response` 会降低置信度

## 常见场景解读

### 场景 1：高相似度 + 高置信

```
相似度: 0.92 | 置信: high
```

**解读**：测试结果与该基线高度吻合，极大概率是同一模型或相近模型家族。

**行动建议**：如果该基线是你信任的官方接口，说明你当前的 API 很可能就是真实来源。

---

### 场景 2：中等相似度 + 中置信

```
相似度: 0.71 | 置信: medium
```

**解读**：结果与基线部分吻合，但存在明显差异。可能原因：
- 模型本身发生了版本迭代（基线是旧版本）
- 中转平台进行了动态路由（部分请求被分发到不同模型）
- 测试参数不一致（温度、max_tokens 不同）

**行动建议**：
1. 核对测试参数是否与基线完全一致
2. 尝试用更多探针重新测试
3. 检查是否有高频的错误类型（如大量空响应）

---

### 场景 3：低相似度 + 低置信

```
相似度: 0.38 | 置信: low
```

**解读**：测试结果与该基线显著不符。可能原因：
- 确实是不同的模型
- API 中转平台偷换了模型（降级）
- 网络问题导致部分请求失败

**行动建议**：
1. 先排除技术问题（检查是否有大量 `empty_response` 或超时）
2. 与其他已知基线对比，看是否能匹配到其他身份
3. 记录该中转平台的名称和行为，向社区报告

## 误判的常见原因

### 1. 温度参数不一致

如果基线在 `temperature=0` 下生成，而你测试时使用 `temperature=0.7`：
- 选项题的随机性会增加
- 相似度分数会被人为拉低
- **解决**：确保基线和测试使用相同的温度值

### 2. 模型版本迭代

模型厂商会在不通知的情况下更新模型权重。例如：
- 某基线在半年前用 GPT-4 建立，现在厂商已更新到更新的版本
- 新版本的回答模式可能略有不同
- **解决**：定期使用官方接口更新基线

### 3. 动态路由（Dynamic Routing）

许多中转平台会在后端动态切换模型：
- 低负载时用大模型，高负载时用小模型
- 不同类型的请求分发到不同模型
- **表现**：多次运行结果波动大，相似度不稳定
- **解决**：在高峰期和低峰期分别测试，观察结果是否一致

### 4. 探针泄漏（Probe Leakage）

如果某道探针的题目和答案已经出现在模型的训练数据中：
- 模型可能“背诵”出答案，而非真正的推理
- 测试结果不能反映模型的真实能力
- **解决**：Self-Awakening 会标记高泄漏风险的探针，解读报告时请关注 `leak_risk` 字段

## 报告的使用边界

### ✅ 适合的场景

- 验证中转平台是否提供了与声称相符的模型
- 比较两个不同 API 的实际表现差异
- 监控同一 API 在不同时间段的表现稳定性
- 研究不同模型在特定任务上的能力指纹

### ❌ 不适合的场景

- 将概率推断作为绝对证据用于法律诉讼
- 在单次 8 题测试的基础上得出"100% 确定"的结论
- 绕过付费墙或劫持他人 API 进行审计
- 将报告用于恶意抹黑竞争对手

## 报告语言规范

Self-Awakening 生成的报告应遵循以下语言规范：

| 推荐表述 | 避免表述 |
|---------|---------|
| "与基线 X 相似度 0.89" | "100% 是模型 X" |
| "置信度：medium" | "确认就是 X" |
| "存在显著差异，建议进一步验证" | "该平台在作弊" |
| "建议使用 51 题探针重新测试" | "结论确定" |

## 如何提高报告可信度

1. **增加探针数量**：使用全部 51 题而非仅 8 题核心集
2. **多次运行取均值**：同一 API 运行 3 次，计算平均相似度
3. **固定所有参数**：确保 temperature、max_tokens、endpoint 完全一致
4. **使用新鲜基线**：优先使用最近创建的基线而非半年前的旧基线
5. **对比多个基线**：同时与 2-3 个不同模型基线对比

## 供应商申诉流程

如果你认为某份报告对你的服务存在误判，可以通过以下步骤申请修正：

1. 在 GitHub Issues 提交申诉，标题注明 `[Appeal]`
2. 提供你的服务在相同参数下的官方运行结果（JSON）
3. 说明你认为报告存在问题的具体原因
4. 等待 Self-Awakening 团队审核（通常 7 个工作日内）

---

> **记住**：Self-Awakening 是透明度工具，不是审判工具。它的目的是帮助用户获得知情权，而不是给供应商定罪。保持严谨和善意，才能让这个工具长期服务于整个 AI 生态。
